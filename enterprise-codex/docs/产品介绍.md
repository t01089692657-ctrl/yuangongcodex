# 企业级 Codex 统一分发平台 —— 产品介绍

## 一句话

让全公司员工"开箱即用" OpenAI Codex：员工通过企业身份（飞书）登录一个客户端就能直接用上 Codex，**用量可统计、权限可管控、离职即失效**，并且公司可以把自己的**规范和技能**统一推送到每个人的 Codex 里。

这正是那个演示视频里展示的产品形态——只不过视频里的服务端是一个"中转站"（和开源的 sub2api 同类），而本产品把**服务端网关**和**客户端封装**都完整实现了，并且默认走**合规**的接入方式（用公司自己的 OpenAI/Azure Key，而不是拼车个人订阅号）。

---

## 它解决什么问题

没有这个平台时，让 100 个员工都用上 Codex 意味着：

- 每个人自己去搞 API Key、改 `~/.codex/config.toml`、`auth.json`，写一份 SOP 照着做——麻烦、易错。
- Key 散落在每个人手里，**用量看不见、成本算不清**。
- 员工离职后，发出去的 Key **收不回来**，还在消耗公司额度、存在数据外泄风险。
- 公司的编码规范、内部工具（MCP）**没法统一下发**，每个人的 Codex 行为不一致。

本平台把这些全部收口到"一个客户端 + 一个后台"。

---

## 两个平面（产品架构）

平台由两个平面组成，分别对应"接入/计费"和"分发/管控"：

### 平面 A —— 网关（Gateway，服务端）
一台服务器上运行的 AI API 网关，对员工暴露一个 **OpenAI 兼容**的地址：

- **签发 Key**：员工经身份校验后，网关签发一把带身份绑定的 Key（`sk-comp-…`）。
- **计量转发**：把 Codex 的请求（Responses API）用**公司自己的上游 Key**转发给 OpenAI/Azure，并逐 token 记账。
- **管控**：按人限并发/限速；一键或自动**吊销** Key（下一次请求立刻 401）。
- **技能下发接口**：把公司的 `AGENTS.md`、prompts、MCP 配置作为清单供客户端拉取。

> 这一层的职责，和 sub2api 这类"中转站"是同一类——但本产品默认对接**官方 API Key**（合规），而不是池化个人订阅账号。

### 平面 B —— 客户端（Client，员工机器）
员工桌面端的封装（视频里的"客户端"），一条命令跑完全部动作：

```
飞书 SSO 登录 → 网关签发 Key → 写入托管的 Codex 配置 → 同步公司技能 → 启动已内置的 Codex
```

员工**什么都不用配**：不用申请 Key、不用改配置文件、不用操心网络。Codex 已经打包在客户端里，客户端只负责把 Key 和公司规范注入进去再拉起它。

### 管理者后台（Manager Console）
一个网页控制台，**只有管理者能进**（普通员工登录被拒 403）：

- 每位员工的 **token 用量 + 排行榜**、在职/离职状态。
- **一键吊销**某个员工的访问（并记录操作人，可审计）。
- 管理者本人也通过**飞书 SSO 登录**，与普通员工身份区分开。

## 核心能力清单

| 能力 | 说明 |
|---|---|
| 🔐 企业身份登录 | 员工与管理者都用飞书（Feishu/Lark）SSO；网关校验**签名断言**后才签发凭据，杜绝"填个邮箱就冒充"。 |
| ⚡ 员工零配置 | 客户端自动写 `config.toml` + `auth.json`，注入 `base_url` 与 Key，直接拉起内置 Codex。 |
| 📊 用量统计与排行 | 逐 token 记账，按人聚合，后台看谁用得多。 |
| 🧩 统一推送技能 | `AGENTS.md`（编码规范）、`prompts/*.md`（斜杠命令）、公司 **MCP 工具**——改一次，全员生效。 |
| 🚪 离职即失效 | 对接飞书人事事件：员工被标为「离职」→ webhook → **该员工所有 Key 立刻失效**；也可后台手动吊销。 |
| 👔 管理者/员工隔离 | 基于 `isAdmin` 的角色校验，每次请求实时复核；被降权/离职的管理者会话立即失效。 |
| 🛡️ 合规优先 | 默认用**公司自有** OpenAI/Azure Key，而非池化个人订阅（后者违反 OpenAI 条款、有封号风险）。 |
| 🔒 安全默认值 | 生产模式若密钥仍是默认值**拒绝启动**；会话 Cookie 默认 `HttpOnly`/`SameSite=Strict`/`Secure`；webhook 带时间戳防重放；技能写入做路径围栏防越权。 |

## "只能通过我的产品用 / 离职就用不了"——能做到什么程度

诚实地说清楚强制力边界（这是产品设计的关键）：

- **软性收口（默认，够用）**：员工的 Codex 指向公司网关，用的是公司签发的 Key。离职 → 吊销 Key → 他手上的 Codex **立刻拿不到模型**。这覆盖了绝大多数"离职即断"的诉求。
- **它不能阻止**技术型员工在**自己的机器**上把 `config.toml` 的 `base_url` 改指到别处、用他**自己的** OpenAI Key 继续用 Codex 这个开源二进制——因为配置文件在他本地、可编辑。
- **要做到真正"只能在我的产品里用"**，需要控制**运行环境**：把 Codex 跑在公司托管的开发环境 / 受控设备（MDM）/ devcontainer 里，锁住配置与出网。这是可选的加固方向，不在 MVP 范围内。

## 合规与风险（务必阅读）

- ✅ **推荐**：网关对接公司自有的 **OpenAI Platform / Azure OpenAI** API Key 或企业合同额度。这是被官方认可的程序化用法。
- ⛔ **不要**：把个人 ChatGPT/Codex **订阅账号**池化后分发给他人（sub2api 这类中转站的做法）——这违反 OpenAI/Anthropic 服务条款，有**封号**风险；sub2api 自己的 README 也如此警告，并声明不授权商用。
- 本平台把"分发/计费/管控/技能"的价值都保留了，同时把接入换成合规通道。

---

## 技术栈与形态

- **零第三方依赖**，纯 Node.js（≥20）内置模块实现，易审计、易部署。
- 存储用本地 JSON 文件起步（`store.json`），生产可平滑替换为 PostgreSQL/Redis（接口不变）。
- 服务端可跑在一台 Mac mini / Linux 服务器上；客户端为命令行封装，后续可用 Electron/Tauri 打包成桌面 App。
